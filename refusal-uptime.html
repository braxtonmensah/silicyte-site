Refusal uptime: did your agents’ guardrails actually run?

Claude Code runs each pre-tool guardrail as a separate process with a timeout, and by default a guardrail that times out lets the action through. The agent’s result looks the same as if the guardrail had allowed it. The timeout is logged, but nothing reports it as a share of the actions the guardrail should have checked. On one operator’s fleet of Claude Code agents, one guardrail was absent on 29.8% of the calls it existed to check.

Measured on one Windows laptop with 8 logical CPUs, from 30 Sep to 21 Oct 2026: 3,844 sessions and 261,254 tool calls. Forecasts were written down before each measurement, and every count was computed twice by independent methods. Prepared with AI assistance; not peer reviewed.

The design

To the agent, a timeout and a clean pass look the same.

Claude Code gives every pre-tool guardrail a timeout. If the guardrail does not answer in time, the action goes through unless the hook sets onFailure: "block", an opt-in added in v2.1.295. The transcript records the timeout, but the agent’s tool result is the same as if the guardrail had run and allowed it.

This is a documented design choice that keeps agents fast. It is not a vulnerability. It does mean that whether a guardrail ran has to be measured, because the absence of a refusal does not show it.

The measurement

One guardrail was absent on 29.8% of the calls it existed to check.

The fleet was about ten Claude Code sessions, with their sub-agents, run by one operator on one Windows laptop with 8 logical CPUs. Guardrail budgets were 10 to 15 seconds, the operator’s choice (the documented default is 600 s), and onFailure was not set. Across 3,844 sessions and 261,254 tool calls, from 30 Sep to 21 Oct 2026, we counted how often each guardrail was absent on the calls it existed to check.

Guardrail Calls it existed to check Absent Share absent
Compute guard (gpu_before_cpu, 15 s) 103,85030,92929.8%
Polling guard (no_poll, 10 s) 40,28324,12159.9%

For the compute guard, 30,761 of the 30,929 calls on which it was absent returned a result that was not a refusal. The compute guard’s absence was forecast before the read at 0.20 (band 0.05 to 0.50); it came in at 0.298.

Load

Absence rose with the number of agents running at once.

For the compute guard, counting agents as transcripts active in the same 10 minutes: with one running, absence was 0.2% (5 of 2,258). With 11 or more it was 53.1% (28,569 of 53,831), and with 30 or more it was 79.2%. Agent count is our proxy for load; CPU, memory and disk were not measured.

The same rise held within single days (on 18 Oct, from 2.0% of 51 calls to 70.0%) and within single sessions: of 82 sessions that ran at both low and peak load, 61 were absent more often at peak (per-session means 2.3% vs 37.6%). The rise from one agent to eleven or more was forecast before the read at +0.25 (band +0.05 to +0.60); it came in at +0.529.

A Linux server pinned to 8 cores, running synthetic agents with replicas of the same guards (not Claude Code itself), showed zero absence even at 48 agents (22,824 runs). Why the workstation differs (memory pressure, process start cost, antivirus, a cloud-synced folder) is not yet tested.

Control integrity

Presence is one of four numbers per guardrail.

Whether a guardrail ran is not the only question. We report four numbers for each guardrail and call the set its control integrity.

Number Question Measured
Presence Did the guardrail run? Absent on 29.8% of the calls it existed to check.
Coverage Did it watch every path? 20.5% of 931 protected writes went through a shell path the guard never watched. 38.8% got no verdict at all.
Independence Did the guards fail independently? When the compute guard was absent, the polling guard on the same machine was absent too 99.86% of the time (91.0% the other way round). Guards on one host failed together.
Override How often do agents override the guard? 81.6% of 461 refusals were re-issued with the guard’s own sanctioned override. 95.4% of 18,588 override uses came before any refusal.

A wrong prediction

We predicted covert routing-around on 20% of refusals. It happened on 0.7%.

Before reading the data we predicted that, after a guard refused, agents would reach the same effect through a path the guard does not watch on 20% of refusals. It happened after 4 of 603 refusals across the three guards (0.7%, from a five-call detector, so a lower bound). The forecast was wrong by a wide margin. These agents took the guard’s sanctioned override openly instead.

Growth, an extrapolation from one fleet

On its trend, this fleet’s busy hours reach 30 agents by 26 Nov 2026.

Over the measured period, guard timeouts doubled every 2.8 days. Busy-hour concurrency (the mean of a day’s six busiest 10-minute windows, 10.4 agents on 21 Oct) doubles every 23.8 days. Peak windows already pass 30. On its trend the busy-hour mean reaches 30, where absence was 79%, by 26 Nov 2026.

An extrapolation from one fleet. The 26 Nov 2026 date takes one operator’s trend and projects it onto that fleet’s own measured curve. It is not a measurement, and it is not a forecast for any other fleet.

Audit

Audit frameworks ask whether controls kept operating.

PCI DSS 4.0.1 requirement 10.7.2 says: “Failures of critical security control systems are detected, alerted, and addressed promptly.” SOC 2 Type 2 asks whether controls operated effectively over the period.

Refusal uptime is the share of the calls a guardrail existed to check on which the guardrail was present, computed per guardrail.

Method

Method and limits.

Where a number was forecast before the data was read, this page says so; the others were not pre-registered. Every count was computed twice by independent methods. This page was prepared with AI assistance and is not peer reviewed. The full technical note, with every number and its limits, is in the probe’s repository.

The measurements come from one operator’s fleet of Claude Code sessions on one Windows laptop with 8 logical CPUs, from 30 Sep to 21 Oct 2026. The Linux comparison used synthetic agents running replicas of the guards. The 26 Nov 2026 date is an extrapolation from one fleet. Nothing here describes the security of any vendor’s product.
